# 웹 핵심 개념 지도 (선택 참고)

이 문서는 **정규 커리큘럼(weeks/)의 필수 내용이 아니다.**
[modern-frameworks-guide.md](modern-frameworks-guide.md)가 프레임워크 지도라면,
이 문서는 그보다 더 아래층 — **서버·클라이언트·API·DB·도메인·IP 등 웹의 배관(plumbing)**을 다루는
**교사용 참고 자료**다. 학생이 "그런데 서버가 뭐예요?" 같은 질문을 할 때 5~15분 안에 답할 수 있도록 정리했다.

---

## 왜 정규 수업안에 넣지 않았나

[source-curriculum-map.md](source-curriculum-map.md)의 설계 원칙(중학생 대상 · 56시간 · 「개념을 다 가르치기」가 아니라 「웹 결과물에 필요한 워크플로우만」)에 따라,
본 과정은 Week3~6에서 **정적 사이트 제작·배포**까지만 다룬다.
서버·백엔드·DB는 [week06-profile-deploy.md](../weeks/week06-profile-deploy.md)에서 명시적으로 **Non-goal**로 빠져 있다.
그래도 학생들은 배포 과정에서 자연스럽게 "이 사이트 주소는 왜 이래?", "로그인은 어떻게 만들어요?" 같은 질문을 던지므로,
**실습 없이 개념만** 짚어줄 수 있는 지도를 여기 남긴다.

## 핵심 개념 지도 (교사 5~15분 설명용)

| 개념 | 한 줄 설명 | 학생이 이미 접한 지점 |
|------|-----------|------------------------|
| 클라이언트(Client) | 사용자가 쓰는 브라우저·앱 — "요청하는 쪽" | Week3~ 매일 쓰는 크롬 |
| 서버(Server) | 요청을 받아 처리하고 응답을 돌려주는 컴퓨터 | GitHub Pages/Vercel이 사실 서버 |
| 프론트엔드(Frontend) | 클라이언트에서 보이는 화면 — HTML/CSS/JS | Phase1~2 전체 |
| 백엔드(Backend) | 서버에서 돌아가는 로직 — 로그인 처리, 데이터 저장 등 | 아직 미도입 (Supabase가 대체) |
| API | 프론트엔드와 백엔드(또는 다른 서비스)가 데이터를 주고받는 **약속된 창구** | 캡스톤에서 공공데이터 API 쓸 때 |
| DB(데이터베이스) | 데이터를 저장·검색하는 저장소 | Supabase 사용 시 처음 접함 |
| 도메인(Domain) | 서버의 IP 주소를 사람이 외우기 쉬운 이름으로 바꾼 것 (예: `github.com`) | Week6 "도메인 사고 싶어요" 질문 |
| IP 주소 | 인터넷에 연결된 컴퓨터(서버)의 실제 주소 (예: `192.0.2.1`) | 도메인 설명 시 함께 언급 |
| DNS | 도메인 이름을 IP 주소로 바꿔주는 인터넷의 "전화번호부" | 도메인 연결 시 개념만 |
| HTTP/HTTPS | 클라이언트-서버가 데이터를 주고받는 통신 규칙. `S`는 암호화(보안) | 브라우저 주소창 자물쇠 아이콘 |
| 포트(Port) | 한 서버 안에서 여러 서비스를 구분하는 문 번호 (예: `:3000`) | `npm run dev` 후 `localhost:5173` |
| 호스팅(Hosting) | 내 웹사이트 파일을 인터넷에 항상 켜져 있는 서버에 올려두는 것 | GitHub Pages/Vercel이 곧 호스팅 |

> Week6에서 GitHub Pages/Vercel에 배포하는 순간, 이미 「호스팅 = 남의 서버를 빌려 쓰는 것」을 실습한 것이다.
> 이 개념 지도는 그 경험에 이름을 붙여주는 역할만 한다.

## 그림으로 설명하기 (칠판/화이트보드용)

```
[클라이언트]  --- 요청(Request) --->  [서버]
 (브라우저)                          (컴퓨터 어딘가)
              <--- 응답(Response) ---

예: 브라우저에서 github.com 접속
1. 도메인(github.com) → DNS가 IP 주소로 변환
2. 그 IP 주소의 서버에 "index.html 주세요" 요청 (HTTP)
3. 서버가 파일을 응답으로 돌려줌
4. 브라우저가 받은 HTML/CSS/JS를 화면에 그림
```

**설명 포인트:** 학생들이 Week3~6에 만든 사이트도 정확히 이 흐름을 탄다 —
다만 "서버" 역할을 GitHub Pages/Vercel이 대신 해주고 있었을 뿐이다.

## API를 실감나게 설명하는 비유

> **식당 비유:** 손님(클라이언트)이 메뉴판(API 명세)을 보고 주문(요청)하면,
> 주방(서버)이 요리해서 종업원(API)이 음식(응답)을 가져다준다.
> 손님은 주방에 직접 들어가지 않는다 — **정해진 창구로만** 주고받는다.

캡스톤에서 공공데이터 API·Supabase를 쓰는 학생에게는 이 비유 + 아래 한 줄이면 충분하다:
> "너희가 만드는 화면(프론트엔드)이 손님, API는 종업원, 데이터는 주방에서 나오는 음식이야."

## 학생이 흔히 헷갈리는 것 (FAQ)

**Q. GitHub Pages/Vercel도 서버인가요?**
A. 맞다. 다만 "코드를 직접 관리하는 서버"가 아니라 **정적 파일을 대신 호스팅해주는 서버**다.
로그인·DB 처리처럼 "코드가 실행되는" 서버(백엔드)는 아직 이 과정에서 다루지 않는다.

**Q. localhost:5173은 뭔가요?**
A. `npm run dev`로 **내 컴퓨터 안에서 임시로 띄운 서버**다. `localhost`는 "지금 이 컴퓨터"라는 뜻,
`5173`은 포트 번호. 인터넷에 공개되지 않고 나만 볼 수 있다 — Week6에서 배포해야 남들도 볼 수 있다.

**Q. 도메인은 왜 사야 하나요? GitHub Pages 주소는 안 되나요?**
A. `깃허브아이디.github.io`도 이미 도메인이다 (GitHub이 소유한 도메인의 일부를 빌려 쓰는 것).
`내이름.com`처럼 직접 사려면 비용이 들고, 보호자 결제가 필요해 수업 범위 밖 — [week06-profile-deploy.md](../weeks/week06-profile-deploy.md) 참고.

**Q. 로그인 기능은 왜 못 만드나요?**
A. 로그인은 "누가 요청했는지" 서버가 안전하게 기억해야 해서 **백엔드 + DB**가 필요하다.
이 과정은 정적 사이트(Phase1~2) 표준이라 다루지 않지만, 캡스톤에서 필요하면 Supabase로 우회한다 —
[tech-stack.md](tech-stack.md)의 선택 항목 참고.

## 하지 않는 것 (설계 원칙 재확인)

- 서버 직접 구축·배포(Node.js 백엔드 서버 등)
- DB 스키마 설계·SQL 정규 수업
- 네트워크 계층(TCP/IP, OSI 7계층 등) 깊이 있는 설명
- 보안(인증·인가, 암호화 원리) 정규 도입

→ 필요하면 **캡스톤 이후, 개별 자율 학습**으로 안내한다. 정규 수업 안에는 "개념만" 넣는다.
