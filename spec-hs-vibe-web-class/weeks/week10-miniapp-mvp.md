## 🔴 3단 아키텍처 실습: Vercel · Render · Supabase (선택)

**언제 선택하나:** 미니앱이 데이터 저장 + 서버 로직(인증 검증, 외부 API 키 은닉, 복잡한 계산 등)을 함께 다뤄야 할 때. 저장만 필요하고 로직은 단순하면 Supabase를 프론트에서 직접 호출하는 더 가벼운 구성도 가능하지만, **이번 학기 표준은 3단 분리**로 간다 — 6주차 `why-3tier` 워크시트의 "클라이언트/서버/DB" 개념을 실제 배포로 완성하는 것이 목적.

| 계층 | 역할 | 서비스 |
|------|------|--------|
| 프레젠테이션 | 화면(UI) | **Vercel** (또는 GitHub Pages) |
| 애플리케이션 | 요청 처리 · 비즈니스 로직 · 인증/키 은닉 | **Render** (Flask/Express 서버) |
| 데이터 | 저장·조회 | **Supabase** (Postgres) |

**왜 이렇게 나누나:** Supabase 키를 프론트에 그대로 두면(anon key) 브라우저 개발자도구에서 누구나 키를 볼 수 있다. 서비스 role key나 민감한 로직(예: 관리자만 삭제 가능)은 **백엔드(Render) 안에만 두고, 프론트는 백엔드 API만 호출**하게 하면 안전하다 — 이게 3단으로 나누는 실질적 이유.

**절차 (Block B~D에서 나눠 진행):**
1. Supabase 프로젝트 생성 + 테이블 1개 설계 (예: `posts` — 컬럼 3~5개) — DB 계층은 이 순간부터 이미 서비스 중 (Block B)
2. 백엔드(Flask 또는 Express) 서버 작성 — Supabase 서버 클라이언트로 CRUD API 엔드포인트 1~2개 (`GET /items`, `POST /items`) 구현 (Block B~C)
3. 백엔드를 **Render**에 배포: GitHub repo 연결 → Web Service 생성 → 환경변수(`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`)를 Render 대시보드에 등록 → 배포 URL 확인 (Block C)
4. 프론트를 **Vercel**에 배포하고, 프론트 환경변수에 Render API URL을 등록 → `fetch`로 백엔드 API 호출 (Block D)
5. 배포된 프론트 URL에서 새로고침해도 데이터가 남아있는지 확인 (완료 기준)

**주의:**
- Render 무료 티어는 **15분 미사용 시 슬립** → 첫 요청이 30~60초 느릴 수 있음. 시연 직전에 한 번 깨워두라고 미리 안내
- Supabase `SERVICE_KEY`는 절대 프론트/공개 저장소에 노출하지 않고 Render 환경변수에만 둔다 — 이게 3단 분리의 핵심 이유임을 강조
- 시간이 부족하면 2번(백엔드 서버 작성)까지만 하고 Render 배포는 다음 주로 넘겨도 됨 — 「오늘은 여기까지」 선 긋기 원칙 그대로 적용
