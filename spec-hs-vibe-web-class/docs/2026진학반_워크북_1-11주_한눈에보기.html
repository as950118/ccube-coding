1. 11주 로드맵 — 3~11주차

세 덩어리로 기억한다 — 도구 → 웹 서비스 → 서비스에 AI. 아래 칸은 그 주에 남은 결과물(파란 알약)과 핵심 키워드.

시험·면접 포인트

  • 면접에서 「11주 동안 뭘 했나요?」에는 이 그림의 3덩어리 순서로 말한다.
  • 각 주의 결과물은 앞 주 위에 이어서 쌓였다 (BBS는 v0→v3로 같은 폴더를 계속 확장).

2. AI 도구 다루기 — 3~5주

AI에게 시키는 방법(루프)과 맡기는 방식(Plan → 권한 → 기록)을 한 장에.

시험·면접 포인트

  • 「검증」은 사람의 일 — LLM은 틀릴 수 있다 · 앞을 잊는다 · 비밀을 지켜 주지 않는다.
  • 삭제·모르는 명령은 Deny 또는 교사 확인. 「무조건 Allow all」은 쓰지 않는다.

3. 3단 구조와 BBS v0 — 6주

웹 서비스의 뼈대. 손님(브라우저) → 주방(Flask) → 창고(SQLite)가 정해진 창구(라우트)로만 주고받는다.

시험·면접 포인트

  • GET = 조회, POST = 보내서 저장. 입력값은 SQL에 이어 붙이지 않고 ?로 넘긴다(SQL Injection 방지).
  • 「왜 셋으로 나눴나?」 → 역할을 분리해야 고치기·확장하기 쉽다.

4. HTTP 요청과 응답 — 6주

브라우저와 서버는 HTTP라는 약속으로 대화한다. 요청은 메서드·URL·본문·쿠키, 응답은 상태 코드·내용.

시험·면접 포인트

  • GET과 POST의 차이, 상태 코드 200·302·403·404의 뜻을 말할 수 있어야 한다.
  • 쿼리스트링(?q=…)은 URL 뒤에 붙어 조건을 전달한다 (9주 검색).

5. 기본키와 외래키 — 6·7·9주

PK는 행의 이름표, FK는 다른 표의 이름표를 적어 둔 열. 점선 화살표가 가리키는 행이 연결된 데이터다.

시험·면접 포인트

  • posts의 user_id가 1이면 users에서 id가 1인 mina가 쓴 글이다.
  • 면접 단골: 「기본키와 외래키의 차이와 사용한 곳」 → posts.user_id, comments.post_id.

6. BBS 진화 v0 → v3 — 6~9주

하나의 프로젝트가 4주 동안 층층이 자랐다. 한 주에 하나의 새 개념만 얹었다.

시험·면접 포인트

  • 면접에서 「가장 크게 만든 프로젝트」는 이 그림 순서로 설명한다 (구조 → 로그인 → 외부 데이터 → 상호작용).
  • 기능이 늘수록 테이블·파일이 어떻게 늘었는지를 같이 말하면 설계를 이해하고 있다는 신호가 된다.

7. 가입 → 로그인 → 권한 검사 — 7주

로그인은 인증, 수정 가능 여부는 인가. 두 검사 모두 서버에서 한다.

시험·면접 포인트

  • 비밀번호는 해시로 저장 → DB가 유출돼도 원문을 알 수 없다. 로그인 땐 해시끼리 비교.
  • 버튼을 숨기는 것만으로는 부족 — URL로 직접 접근해도 서버가 막아야 한다.
  • 세션이 필요한 이유: 웹 요청은 매번 독립적이라 서버가 방금 로그인한 사람을 잊기 때문.

8. 테이블 관계 (1 : N) — 6·7·9주

한 사람이 글 여러 개, 한 글에 댓글 여러 개. N쪽에 FK를 둔다.

시험·면접 포인트

  • 1:N 구현 한 줄 요약 → 「N쪽 테이블에 1쪽의 id 컬럼(FK)을 넣는다」.
  • 7주 posts.user_id(작성자 연결) · 9주 comments.post_id(어느 글의 댓글) · users.role(RBAC).

9. API와 JSON — 8주

API는 프로그램끼리 쓰는 창구, JSON은 그 창구가 주는 데이터 형식. 받은 JSON에서 필요한 값만 파싱한다.

시험·면접 포인트

  • API 호출 3요소: 주소(엔드포인트) · 요청(파라미터+인증키) · 응답(JSON).
  • 8주 공공데이터, 10주 OpenAI, 11주 나이스 도구 호출 모두 같은 구조다.

10. 외부 API → 대시보드 — 8주

이번엔 우리 서버가 손님. 수집(API) → 가공(파싱) → 표현(대시보드) = 탐구 보고서의 흐름과 같다.

시험·면접 포인트

  • 인증키는 코드에 쓰지 않고 .env → .gitignore로 저장소에 올리지 않는다.
  • 파싱 = 받은 JSON에서 필요한 값만 꺼내 정리. 실패해도 샘플 JSON으로 화면은 뜬다.

11. 요청/응답 vs WebSocket — 9주

지금까지는 브라우저가 먼저 묻는 방식. 채팅만 서버가 먼저 보내는 방식을 썼다.

시험·면접 포인트

  • 댓글·검색·권한은 전부 요청/응답 4단계(요청 → 코드 실행 → 응답 → 화면 갱신).
  • AI가 짠 채팅 코드는 붙여넣기만 하지 말고 send_message가 서버에서 broadcast로 퍼지는 흐름을 설명할 수 있어야 한다.

12. 웹 서비스에 AI 붙이기 — 10주

AI는 검색창이 아니라 서비스의 부품. 기존 Flask 서버에 외부 LLM API가 하나 더 붙었다.

시험·면접 포인트

  • 키는 서버에서만 호출 — 브라우저 코드는 누구나 볼 수 있다.
  • 환각 대응 2가지: ① 시스템 지침(원문에 없으면 「확인 필요」) ② Grounding(공공데이터를 먼저 조회해 근거로 제공).

13. 단일 대화 vs 연속 대화 — 10주

챗봇이 앞말을 아는 비밀: 이전 대화를 매번 같이 보내는 것.

시험·면접 포인트

  • 면접 단골 — 「챗봇은 어떻게 기억하나요?」 → 기록 리스트를 우리가 관리해서 매 요청에 함께 전송.
  • 그래서 대화가 길어지면 보내는 양이 늘고, 서버가 꺼지면 기록도 사라진다.

14. 에이전트 · 하네스 · MCP — 11주

모델 + 도구 + 루프 = 에이전트. 그 루프를 모델 바깥에서 돌려 주는 프로그램이 하네스, 도구를 꽂는 표준이 MCP.

시험·면접 포인트

  • 「AI가 직접 나이스에 접속한다」는 오해 — 모델은 요청만, 실제 실행은 하네스가 내 코드(도구)를 호출.
  • 10주 챗봇의 급식 조회도 이미 최소 에이전트였다 (모델 판단 → 우리 코드 실행 → 결과 재전달).
  • MCP로 만든 도구는 MCP를 지원하는 어느 하네스에서도 쓸 수 있다 (AI용 USB-C).

15. 전체 지도 — 3~11주차

11주 동안 쌓은 것을 한 지도에. 각 칸의 작은 글씨는 그 기능을 만든 주.

시험·면접 포인트

  • 프로젝트를 설명할 땐 이 지도에서 안쪽(서버·DB) → 바깥쪽(외부 API·AI) 순서로 손가락으로 짚는다.
  • 14주 발표에서는 내 캡스톤이 이 지도의 어느 칸과 이어지는지 표시해 보자.

외워 두면 편한 비유 4개

식당 비유클라이언트 · 서버 · DB는 손님 · 주방 · 창고. 우리 서버가 손님이 되면 외부 API.
조교 비유LLM은 아주 많이 읽은 조교. 초안은 빠르지만 틀릴 수 있어 검증은 내 몫.
두뇌와 손 비유모델은 손 없는 두뇌, 도구는 손, 하네스는 둘을 잇는 몸.
USB-C 비유MCP는 도구를 어느 하네스에나 꽂는 표준 규격.
