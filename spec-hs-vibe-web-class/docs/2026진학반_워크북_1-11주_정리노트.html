2. 웹 핵심 개념 — 모든 주차의 바탕

주차별 내용을 읽기 전에 웹 서비스 전체에 공통으로 쓰이는 개념부터 정리한다. 6~11주의 모든 기능은 이 개념 위에 쌓였다.

2.1. 3단 구조(3-tier)

웹 서비스는 맡은 일에 따라 세 층으로 나눈다. 층을 나누면 한 층을 고쳐도 다른 층이 영향을 덜 받는다. (식당의 손님 · 주방 · 창고에 비유한다.)

층하는 일 (이 수업에서)
프레젠테이션 층 (클라이언트)사용자가 보고 누르는 화면. 브라우저와 HTML 템플릿. 프론트엔드라고도 부른다.
애플리케이션 층 (서버)요청을 받아 무엇을 할지 처리하는 로직. Flask의 라우트, 세션·권한 검사. 백엔드라고도 부른다.
데이터 층 (DB)데이터가 실제로 저장되는 곳. SQLite의 bbs.db 파일.
None
클라이언트 --요청(Request)--> 서버 --SQL 조회·저장--> DB
(브라우저)  <--응답(Response)--  (Flask) <------- 결과 -------- (SQLite)
  • 클라이언트는 DB에 직접 접근하지 않는다. 반드시 서버의 정해진 창구(라우트)를 거친다.
  • 권한 검사·비밀번호 확인 같은 중요한 판단은 서버에서 한다. 브라우저 코드는 누구나 볼 수 있기 때문이다.
  • 세 층의 이름과 역할을 설명할 수 있다.
  • 「왜 층을 나누는가」를 한 문장으로 말할 수 있다.
  • 중요한 검사를 서버에서 해야 하는 이유를 설명할 수 있다.

2.2. HTTP — 요청과 응답

브라우저와 서버는 HTTP라는 약속에 따라 대화한다. 요청 하나에는 메서드 · 주소(URL) · (필요하면) 보내는 데이터가 들어 있고, 응답 하나에는 상태 코드 · 내용이 들어 있다.

키워드한 줄 정의
URL서버 안의 자원을 가리키는 주소. http://localhost:5001/posts/3
메서드요청의 종류. GET은 조회, POST는 보내서 저장·수정·삭제. (REST 규칙에서는 PUT·DELETE도 쓰지만 이 수업은 GET·POST만 쓴다.)
쿼리스트링URL 뒤 ?key=value. 검색어 같은 조건을 전달한다. /?q=급식
폼 데이터POST 요청의 본문에 담겨 가는 입력값. 서버는 request.form으로 읽는다.
상태 코드응답 결과를 알리는 숫자. 200 성공 · 302 다른 주소로 이동(redirect) · 403 권한 없음 · 404 없는 주소 · 500 서버 오류
localhost / 포트내 컴퓨터를 가리키는 주소 / 프로그램이 문을 여는 번호. 이 수업은 5001번을 쓴다.
쿠키브라우저가 보관했다가 요청마다 함께 보내는 작은 정보. 세션 식별에 쓰인다.
Python
@app.route("/posts/<int:post_id>")   # GET /posts/3
def detail(post_id):
    ...
    return render_template("detail.html", post=post)   # 200 + HTML
  • GET과 POST를 언제 쓰는지 설명할 수 있다.
  • 상태 코드 200, 302, 403, 404의 뜻을 말할 수 있다.
  • 브라우저 주소창의 URL에서 경로와 쿼리스트링을 구분할 수 있다.

2.3. API와 JSON

API(Application Programming Interface)는 프로그램끼리 요청을 주고받는 약속된 창구다. 사람은 화면을 보지만, 프로그램은 API로 데이터를 직접 주고받는다. 8주차에는 공공데이터 API를, 10주차에는 OpenAI API를 호출했다.

키워드한 줄 정의
API다른 프로그램이 쓸 수 있도록 공개한 요청·응답 창구. 메뉴판(명세)을 보고 주문(요청)하는 것과 같다.
엔드포인트API의 주소. 서버의 라우트도 하나의 엔드포인트다.
JSONAPI가 주고받는 데이터 형식. {"키": 값} 형태의 글자 데이터.
인증키(API 키)「내가 누구인지」 API 서버에 증명하는 열쇠. 코드에 쓰지 않고 .env에 보관한다.
파싱받은 JSON에서 필요한 값만 꺼내 정리하는 것.
SDK / 라이브러리API 호출을 쉽게 해 주는 도구. requests(HTTP 호출), openai(OpenAI 호출).
Python
res = requests.get(URL, params={"serviceKey": KEY, "stationName": "종로구"})
data = res.json()                          # JSON → 파이썬 딕셔너리
item = data["response"]["body"]["items"][0]
print(item["stationName"], item["pm10Value"])

서버 입장에서 보면 두 가지 역할이 있다. 브라우저의 요청에 응답하는 주방이면서, 외부 API에 요청하는 손님이 되기도 한다.

  • API를 한 문장으로 정의할 수 있다.
  • API 키를 코드에 직접 쓰면 안 되는 이유를 설명할 수 있다.
  • JSON에서 필요한 값만 꺼내는 과정을 설명할 수 있다.

2.4. 데이터베이스 — 테이블 · 기본키 · 외래키

관계형 DB는 데이터를 표(테이블) 로 저장한다. 표 한 줄이 행(row), 한 칸의 이름이 열(column) 이다. 표끼리는 키(key) 로 연결한다.

키워드한 줄 정의
테이블같은 종류의 데이터를 모은 표. users, posts, comments
행 · 열행은 데이터 한 건(글 하나), 열은 항목(title, content).
기본키 PK (Primary Key)행을 하나로 구분하는 열. 중복되거나 비어 있으면 안 된다. 보통 id.
외래키 FK (Foreign Key)다른 테이블의 기본키를 가리키는 열. posts.user_id는 users.id를 가리켜 글과 작성자를 연결한다.
UNIQUE같은 값이 두 번 들어갈 수 없게 하는 제약. 아이디 중복 방지에 쓴다.
1:N 관계한 행에 여러 행이 연결되는 관계. 사용자 1 : 글 N, 글 1 : 댓글 N. N쪽 테이블에 FK를 둔다.
CRUDCreate(INSERT) · Read(SELECT) · Update · Delete. 데이터를 다루는 네 가지 기본 동작.

users 테이블과 posts 테이블 예시

None
users                          posts
id(PK) | username | role       id(PK) | title    | user_id(FK)
   1   | mina     | user          1   | 첫 글    |     1     ──▶ users.id = 1 (mina)
   2   | admin    | admin         2   | 공지     |     2     ──▶ users.id = 2 (admin)
                                  3   | 두 번째  |     1     ──▶ users.id = 1 (mina)
SQL
CREATE TABLE posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,   -- 기본키
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    user_id INTEGER REFERENCES users(id)    -- 외래키
);
SELECT * FROM posts WHERE user_id = ?       -- 이 사용자가 쓴 글만

⚠️ SQL 문장에 입력값을 문자열로 이어 붙이면 SQL Injection에 노출됩니다. 값은 항상 ? 자리에 따로 넘깁니다.

  • 기본키와 외래키의 차이를 예로 설명할 수 있다.
  • 1:N 관계를 DB로 표현하는 방법(N쪽에 FK)을 말할 수 있다.
  • ? 바인딩을 쓰는 이유를 설명할 수 있다.

2.5. 프론트엔드 · 백엔드 · 세션

키워드한 줄 정의
프론트엔드사용자가 보는 화면을 만드는 쪽. HTML(구조) · CSS(모양) · JavaScript(동작).
백엔드요청을 처리하고 데이터를 다루는 쪽. 이 수업에서는 Python Flask.
템플릿서버가 데이터를 끼워 넣어 HTML을 완성하는 틀. render_template.
세션웹 요청은 매번 독립적이라 서버가 방금 로그인한 사람을 잊는다. 세션이 로그인 상태를 서버에 기억시킨다.
인증 / 인가인증은 「누구인지」 확인(로그인), 인가는 「무엇을 해도 되는지」 판단(권한).
해시원문을 알 수 없게 바꾼 값. 비밀번호는 해시로 저장한다.
  • 프론트엔드와 백엔드가 맡은 일을 구분할 수 있다.
  • 세션이 필요한 이유를 설명할 수 있다.
  • 인증과 인가의 차이를 예로 설명할 수 있다.

2.6. 보안 기본 습관

  • 비밀(API 키, 비밀번호)은 코드에 쓰지 않고 .env에 둔다. .env는 GitHub에 올리지 않는다.
  • 비밀번호는 해시로 저장한다. 그대로 저장하지 않는다.
  • SQL에는 값을 ?로 넘긴다.
  • 권한 검사는 서버에서 한다. 버튼을 숨기는 것만으로는 부족하다.
  • AI 채팅창에 비밀을 입력하지 않는다. AI의 답은 틀릴 수 있으므로 직접 검증한다.

3. AI 도구 다루기 — 3~5주차

3.1. 3주차 — 바이브코딩 입문

만든 것: 자기소개 웹페이지 index.html. 바이브코딩은 「느낌대로 코딩」이 아니라 목표 → 계획 → 실행 → 검증을 반복하는 방식이다.

키워드한 줄 정의
4단계 루프목표(한 문장) → 계획(파일·화면) → 실행(AI에게 구체적으로) → 검증(브라우저로 확인, 이상하면 처음으로)
LLM많은 글을 학습해 다음 말을 예측하는 AI. 아주 많이 읽은 조교에 비유한다.
모델 vs 도구모델(Claude, GPT)은 뇌, AI 코딩 도구(Cursor, Claude Code)는 폴더의 파일을 직접 읽고 고치는 작업실이다.
LLM의 한계 3가지틀릴 수 있다(검증 필수) · 앞부분을 잊는다(목표 반복) · 비밀을 지켜 주지 않는다.
터미널pwd 지금 위치 · ls 파일 목록 · cd 폴더 이동
None
✗ 웹사이트 만들어줘
✓ 단일 index.html로 자기소개 페이지. 제목·한 줄 소개·관심사 목록. 한국어. 읽기 쉽게.

면접에서는 「AI에게 시키기만 한 게 아니라, 목표를 한 문장으로 정하고 결과를 브라우저로 검증하는 루프로 작업했습니다.」

  • 바이브코딩 4단계를 순서대로 말할 수 있다.
  • 채팅 AI와 AI 코딩 도구의 차이를 설명할 수 있다.
  • AI 채팅에 넣으면 안 되는 정보를 말할 수 있다.

3.2. 4주차 — Plan 모드와 권한

만든 것: Hero · About · Interests · Projects · Contact 5섹션 프로필 웹 초안(v0). 구조를 먼저 정하고(Plan), 위험한 행동은 사람이 허락한다(Permission).

키워드한 줄 정의
Plan 모드「구조 먼저, 코드 나중」. AI가 설계안을 내면 내가 승인·수정·거절한 뒤에 코드를 쓴다.
언제 Plan?파일이 2개 이상 생기거나 섹션이 늘어날 때. 오타·색 하나는 바로 수정한다.
Non-goals이번에 하지 않을 것. 먼저 적어서 범위가 번지는 것을 막는다.
Permission「이 행동을 해도 될까?」를 묻는 안전장치. Accept(진행) / Deny(거부).
/init프로젝트를 분석해 AI용 안내 파일을 만든다.
None
읽기        → 보통 허용
쓰기/수정   → 목표와 맞으면 허용
삭제        → 한 번 더 읽기
모르는 명령 → 교사에게 확인 (curl ... | sh 는 Deny)

⚠️ 실명·학교·전화번호·집주소·얼굴 사진은 프로필에 넣지 않아도 완성입니다. 닉네임과 플레이스홀더로 충분합니다.

면접에서는 「바로 코드를 시키지 않고 Plan으로 섹션 구조와 하지 않을 것을 먼저 합의했습니다. 탐구에서 가설을 세우고 실행하는 순서와 같습니다.」

  • Plan이 필요한 경우와 바로 수정해도 되는 경우를 하나씩 말할 수 있다.
  • 삭제나 모르는 명령을 제안받았을 때 Deny하는 이유를 설명할 수 있다.
  • Non-goals를 적는 이유를 설명할 수 있다.

3.3. 5주차 — Git · GitHub · CLAUDE.md

만든 것: GitHub 저장소(README 5줄 + CLAUDE.md)와 의미 있는 커밋 2개 이상. 작업 기록은 Git에, AI가 기억할 규칙은 CLAUDE.md에 남긴다.

키워드한 줄 정의
status → add → commit → push상태 확인 → 올릴 변경 담기 → 메시지와 함께 기록 → GitHub로 올리기
README저장소의 얼굴이자 포트폴리오의 첫 화면. 프로젝트 설명 5줄.

4. 웹 서비스 만들기 — BBS v0 → v3 (6~9주차)

4.1. 6주차 — 클라이언트 · 서버 · DB (v0)

만든 것: Flask + SQLite 게시판의 목록·상세·작성·수정·삭제 5기능(AI 없이 직접 코딩). 파일을 열면 보이던 페이지에서 데이터가 저장되고 다시 불러와지는 서비스로 넘어갔다.

키워드한 줄 정의
라우트「이 주소로 요청이 오면 이 함수를 실행」. @app.route("/")
CRUD 5기능목록 GET / · 상세 GET /posts/<id> · 작성 POST /posts · 수정 POST …/edit · 삭제 POST …/delete
SQLite설치 없이 파일 하나(.db)로 동작하는 DB.
저장 확인서버를 껐다 켜도 글이 남아 있으면 DB에 저장된 것이다.
Python
@app.route("/")
def index():
    conn = get_db()
    posts = conn.execute("SELECT * FROM posts").fetchall()
    return render_template("list.html", posts=posts)

app.run(debug=True, port=5001)

면접에서는 「화면·처리·저장을 나눈 이유는 역할을 분리해야 고치기 쉽고 확장하기 쉽기 때문입니다. 서버를 껐다 켜도 글이 남는 것으로 DB 저장을 확인했습니다.」

  • 「글쓰기」 버튼 이후의 흐름을 클라이언트 → 서버 → DB 순서로 설명할 수 있다.
  • 서버를 껐다 켜도 글이 남는 이유를 설명할 수 있다.
  • CRUD 5기능이 어떤 라우트와 SQL로 만들어졌는지 말할 수 있다.

4.2. 7주차 — 회원가입 · 로그인 · 권한 (v1)

만든 것: 회원가입/로그인/로그아웃, 작성자 표시, 본인 글만 수정·삭제(users 테이블, posts.user_id). 「누가 썼는지」와 「누가 고칠 수 있는지」를 코드로 정했다.

키워드한 줄 정의
인증 / 인가로그인으로 누구인지 확인 / 본인 글인지 확인해 수정 허용.
세션로그인 상태를 서버가 기억하는 방법. session["user_id"]. secret_key로 서명한다.
비밀번호 해시generate_password_hash로 저장하고 check_password_hash로 비교한다.
외래키posts.user_id가 users.id를 가리켜 글과 작성자를 연결한다.
Python
if "user_id" not in session:                 # 인증: 로그인했나?
    return redirect(url_for("login"))

if post["user_id"] != session["user_id"]:    # 인가: 내 글인가?
    return "권한 없음", 403

⚠️ 버튼만 숨기면 안 됩니다. URL로 직접 접근해도 막히도록 서버에서 반드시 검사합니다.

면접에서는 「비밀번호는 해시로 저장해 DB가 유출돼도 원문을 알 수 없게 했고, 수정·삭제는 서버에서 작성자 본인인지 확인하도록 권한을 구현했습니다.」

  • 인증과 인가의 차이를 예로 설명할 수 있다.
  • 비밀번호를 그대로 저장하면 위험한 이유를 설명할 수 있다.
  • 세션이 필요한 이유를 설명할 수 있다.

4.3. 8주차 — 공공데이터 API와 대시보드 (v2)

만든 것: 에어코리아 미세먼지 API를 opendata.py로 가공해 /dashboard(표 + 막대그래프)로 보여주고, API 실패 시 샘플 데이터로 대체한다. 수집 → 가공 → 표현은 탐구 보고서의 흐름과 같다.

키워드한 줄 정의
오픈 API · 인증키신청하면 누구나 쓰는 공개 API / 나를 증명하는 열쇠.
.env비밀 값을 코드 밖에 보관하는 파일. Git에 올리지 않는다.
파싱받은 JSON에서 필요한 값만 꺼내 정리한다.
예외 처리키가 없거나 인터넷이 끊겨도 앱이 죽지 않고 sample_air_quality.json으로 화면을 띄운다.
Python
key = os.environ.get("PUBLIC_DATA_API_KEY")     # 코드에는 이름만, 값은 .env에

items = raw["response"]["body"]["items"]
result = [{"station": i["stationName"],
           "pm10": int(i.get("pm10Value") or 0)} for i in items]

면접에서는 「API 키는 .env로 분리해 저장소에 올리지 않았고, 외부 API가 실패해도 샘플 데이터로 화면이 뜨도록 예외 처리를 넣었습니다.」

  • 인증키를 .env에 두는 이유를 설명할 수 있다.
  • 파싱이 무엇이고 왜 필요한지 설명할 수 있다.
  • API 실패 시 앱이 죽지 않게 한 방법을 설명할 수 있다.

4.4. 9주차 — 댓글 · 검색 · 관리자 · 실시간 채팅 (v3)

만든 것: 댓글(1:N), 검색(?q=), 관리자 권한(RBAC), 실시간 채팅(WebSocket, AI와 함께). 혼자 쓰는 게시판에서 사람과 사람이 상호작용하는 커뮤니티로 올라갔다.

키워드한 줄 정의
요청/응답 사이클① 브라우저 요청 → ② 서버 코드 실행 → ③ 응답 → ④ 화면 갱신. 댓글·검색·권한 모두 이 4단계다.
1:N 관계글 하나에 댓글 여러 개. comments.post_id가 posts.id를 가리킨다.
쿼리스트링 + LIKE/?q=키워드로 검색어를 보내고, SQL LIKE ?에 %키워드%를 넘겨 포함된 글을 찾는다.
RBAC사용자를 역할(role)로 나눠 역할마다 할 수 있는 일을 다르게 한다. users.role = user / admin.
WebSocket연결을 유지해 서버가 먼저 메시지를 보낼 수 있는 양방향 통신.
Python
is_admin = session.get("role") == "admin"        # RBAC: 역할로 판단

@socketio.on("send_message")                     # 브라우저 → 서버
def handle(data):
    emit("new_message", data, broadcast=True)    # 서버 → 모든 브라우저

면접에서는 「실시간 채팅은 AI와 함께 만들었지만, 코드를 그대로 붙이지 않고 send_message 이벤트가 서버에서 broadcast로 모두에게 전달되는 흐름을 직접 설명할 수 있도록 읽고 확인했습니다.」

  • 1:N 관계를 DB로 표현하는 방법을 설명할 수 있다.
  • 일반 요청/응답과 WebSocket의 차이를 설명할 수 있다.
  • 7주차의 본인 글 검사와 9주차의 역할(RBAC) 검사의 차이를 말할 수 있다.

5. 서비스에 AI 붙이기 — 10~11주차

5.1. 10주차 — AI 서비스 (김반장 school_bot)

만든 것: 공지 요약(단일 대화), 김반장 챗봇(연속 대화), 시간표 사진 분석, 나이스 급식 + AI 해석. AI는 「똑똑한 검색창」이 아니라 우리 서비스의 부품이다.

키워드한 줄 정의

단일 vs 연속 대화단일은 문맥 없는 단발 호출(Stateless). 연속은 이전 대화 기록을 우리가 쌓아 매번 함께 보낸다.
System Instructioninstructions로 역할·응답 규칙을 고정한다. 원문에 없으면 「확인 필요」로 답하게 한다.
환각 / GroundingAI가 지어내는 것(환각) / 공공데이터를 먼저 조회해 근거로 제공해 막는 방법(Grounding).
멀티모달글뿐 아니라 이미지(input_image)도 입력. 시간표·공지 사진에서 텍스트를 추출한다.
None

② Flask → OpenAI     (키 + 지침 + 질문, 서버에서만)
③ 모델이 규칙에 따라 응답 생성
④ Flask → 브라우저   (급식 원문과 AI 해석을 분리해 렌더링)

면접에서는 「AI가 준 답을 그대로 믿지 않도록 키를 숨기고, 규칙을 고정하고, 사실은 공공데이터에서 가져오고, 화면에서 원문과 AI 해석을 구분했습니다.」

  • 챗봇이 앞의 대화를 기억하는 원리를 설명할 수 있다.
  • 환각을 줄이는 방법 두 가지를 말할 수 있다.
  • API 키를 브라우저에서 호출하면 안 되는 이유를 설명할 수 있다.

만든 것: 에이전트 루프 관찰(step5_agent.py), 학사일정 도구 추가, 내 함수를 MCP 서버(school_mcp.py)로 만들어 Claude Code에 연결. AI가 똑똑해 보이는 이유의 절반은 모델이 아니라 모델을 감싼 프로그램(하네스)과 쥐여 준 도구다.

    ...
Shell

6. 면접 예상 질문과 용어 사전

6.1. 면접 예상 질문 12개

오른쪽 칸은 정답이 아니라 답변의 뼈대다. 내 프로젝트의 경험으로 바꿔 말한다.

질문답변 뼈대
1. 바이브코딩이 뭔가요? AI가 다 해주는 것 아닌가요?목표를 한 문장으로 정하고, 계획을 합의하고, AI가 실행한 결과를 내가 검증하는 반복이다. 4주차에 Plan으로 구조를 먼저 정했고 6~9주차 핵심 기능은 AI 없이 직접 코딩했다.
2. AI가 틀린 코드를 줬을 때 어떻게 했나요?LLM은 틀릴 수 있어서 검증이 필수다. 직접 실행해 확인하고, 에러 메시지를 근거로 목표를 구체적으로 다시 적어 재요청했다. (본인의 실제 사례를 하나 넣는다.)
3. 웹 서비스가 동작하는 구조를 설명해 보세요.클라이언트가 요청을 보내면 서버(Flask)가 처리하고, 필요하면 DB(SQLite)에서 읽고 써서 응답한다. 이 3단 구조 위에 로그인·API·AI를 하나씩 얹었다.
4. 기본키와 외래키가 뭔가요? 어디에 썼나요?기본키는 행을 구분하는 열(id), 외래키는 다른 테이블의 기본키를 가리키는 열이다. posts.user_id로 글과 작성자를, comments.post_id로 댓글과 글을 연결했다.
5. 로그인은 어떻게 구현했나요? 비밀번호는 안전한가요?비밀번호는 해시로 저장하고 로그인 시 해시를 비교한다. 로그인하면 세션에 user_id를 저장하고, 수정·삭제는 서버에서 작성자 본인인지 검사한다.
6. 인증과 인가의 차이는?인증은 누구인지 확인(로그인), 인가는 무엇을 해도 되는지 판단(본인 글만 수정, 관리자만 공지 고정)이다.
7. API가 뭔가요? 어떤 API를 써 봤나요?프로그램끼리 요청을 주고받는 약속된 창구다. 에어코리아 공공데이터 API, 나이스 급식 API, OpenAI API를 호출했고, 키는 .env로 관리했다.
8. 외부 API가 실패하면 어떻게 되나요?예외 처리를 넣어 샘플 데이터로 대체해 앱이 죽지 않게 했다. 키를 지우거나 인터넷을 끊고 직접 테스트했다.
9. AI의 환각 문제는 어떻게 대응했나요?시스템 지침으로 「원문에 없으면 확인 필요」로 답하게 했고, 급식·일정은 공공데이터를 먼저 조회해 근거로 줬다(Grounding). 화면에서도 원문과 AI 해석을 분리했다.
10. 챗봇은 어떻게 앞의 대화를 기억하나요?AI가 기억하는 것이 아니라 내 코드가 대화 기록을 쌓아 매번 함께 보낸다. 서버를 재시작하면 기록이 사라지는 한계가 있다.
11. AI 에이전트와 MCP를 설명해 보세요.에이전트는 모델에 도구와 반복 루프가 붙어 목표가 해결될 때까지 도구를 골라 쓴다. MCP는 도구를 어느 하네스에나 꽂는 표준 규격이다. 내 급식 조회 함수를 MCP 서버로 만들어 Claude Code에 연결했다.
12. 11주 동안 가장 크게 배운 점과 시행착오는?(본인 경험) 예: 구조를 먼저 나누는 것이 중요했다, AI에게 맡길 부분과 직접 통제할 부분을 나누는 설계가 핵심이었다. 커밋 히스토리를 근거로 말한다.

6.2. 용어 사전

키워드한 줄 정의
LLM (3주)많은 글을 학습해 다음 말을 예측하는 대규모 언어 모델.
Plan 모드 (4주)코드를 쓰기 전에 설계안부터 합의하는 방식.

완성 확인 목록

  • 그림 페이지의 15장을 보고 각 그림을 말로 설명할 수 있다.
  • 3단 구조에서 요청이 지나가는 길을 순서대로 설명할 수 있다.
  • GET과 POST, 상태 코드 200·302·403·404의 뜻을 말할 수 있다.
  • 기본키와 외래키를 users·posts·comments 예로 설명할 수 있다.
  • API 키를 .env로 관리하는 이유를 설명할 수 있다.
  • 인증과 인가, 세션과 해시의 역할을 설명할 수 있다.
  • 단일 대화와 연속 대화의 차이, 환각을 줄이는 방법을 설명할 수 있다.
  • 에이전트, 하네스, MCP를 한 문장씩 정의할 수 있다.
  • 면접 예상 질문 12개에 내 경험을 넣어 답할 수 있다.

다음 단계는 12~14주차 캡스톤이다. 11주차 숙제(몸풀기 질문지, 한 문장 피치)로 주제를 정하고, 구현 → 포트폴리오 → 면접형 발표로 이어진다. 이 노트의 개념 중 내 프로젝트에 쓴 것을 골라 「왜 그렇게 설계했는가」를 설명하는 연습을 해 둔다.
